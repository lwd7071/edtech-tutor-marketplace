# Kế hoạch triển khai lại UI theo route

## Trạng thái và cổng duyệt

Baseline cập nhật 2026-10-16: **61/70 route đã nghiệm thu**; implementation đi tuần tự từng page. Reference P (2026-10-15), A/S/T/X (2026-10-16) đã được duyệt. Ảnh tạo sinh chỉ là bố cục đề xuất; `PAGE_DESIGN_PLAN.md` và API contract quyết định nội dung/hành vi. Từng route chỉ được PASS khi đủ bằng chứng checklist.

## Quy trình cho một page

1. Chụp trước ở 375/768/1280px bằng app chạy với dữ liệu thật hoặc fixture khớp DTO; ghi nguồn dữ liệu và git baseline. Đọc mục route trong `PAGE_DESIGN_PLAN.md`, UI owner trong `PAGE_INVENTORY.md`, API contract và reference nhóm đã duyệt.
2. Giữ nguyên props, API call, handler, role/ownership, query và transition. Xây lại JSX/layout chính từ đầu theo thứ tự vùng của page spec; đổi CSS cần thiết, không sửa wrapper mỏng để làm đẹp diff. Component chung thay đổi thì ghi danh sách route phụ thuộc.
3. Chạy test route, kiểm tra browser trạng thái chính và chụp sau ở ba viewport. Tính `R/N` trên các dòng JSX/layout render gốc của UI owner như checklist: ít nhất 60% dòng render thực sự thay/xóa vì cấu trúc. Ghi full-file diff để minh bạch phần contract được giữ nguyên; review phần cấu trúc, không lấy numstat làm bằng chứng duy nhất.
4. Điền **mọi ô** trong bảng bên dưới và `UI_ACCEPTANCE_CHECKLIST.md`; chỉ khi đủ ảnh, test, behavior và reference approval mới đánh dấu PASS. Sửa lỗi page này trước khi mở page kế tiếp.

Thứ tự dưới đây là thứ tự thao tác, không phải năm đợt đổi CSS hàng loạt. Public dẫn tới auth; student và teacher dùng các luồng public/auth; admin dùng shell và các pattern list/detail đã ổn định. Cặp `/admin` và `/admin/dashboard` dùng một UI owner, nhưng cần hai lượt route smoke. `BookingWorkspace`, `BookingDetailPage`, `ChatPage`, `NotificationList` dùng chung giữa Student/Teacher: một lần viết lại component, rồi xác minh cả hai role khi mỗi route tới lượt. Backend, migration và API không thuộc phạm vi redesign.
