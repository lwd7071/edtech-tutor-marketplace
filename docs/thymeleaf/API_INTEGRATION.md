# Tích hợp API

## Quy tắc

API/DTO/error chi tiết thuộc [API_CONTRACT.md](../architecture/API_CONTRACT.md) và [ERROR_CODES.md](../architecture/ERROR_CODES.md). Bảng này chỉ là bản đồ trang → code endpoint và nhãn chuyển đổi. Link file nguồn là đường dẫn tương đối repo. Endpoint REST hiện có trả JSON trừ endpoint binary/webhook; các SSR handler đã được lập bản đồ bên dưới và trong [ROUTES_AND_PAGES.md](ROUTES_AND_PAGES.md). Những route/action chưa có code phải được ghi riêng là đề xuất hoặc chưa xác minh, không suy ra từ endpoint REST.

`[ĐÃ CÓ]` = mapping đã có trong backend. `[CẦN ĐỔI ĐỂ PHỤC VỤ HTML]` = endpoint có nhưng trả JSON/API semantics; cần web controller hoặc form/redirect phù hợp. `[ĐỀ XUẤT MỚI]` = capability chưa thấy trong code nhưng được đề nghị thêm. `[CHƯA XÁC MINH]` = code/tài liệu chưa đủ kết luận endpoint/flow. Bảng dưới liệt kê endpoint theo page family; request/response/validation chi tiết chỉ đọc tại API contract.

Adapter/HTML route là layer mới. Không có migration mới được xác định.

## API integration decision map

Với mọi page family, controller hiện tại chỉ chứng minh JSON API capability. Thymeleaf read model lấy từ service/facade tương ứng; command forms gọi service command. Web route/method là handler mới và chỉ tạo khi cần navigation/form HTML. Không tạo API mới chỉ để render HTML. Nguồn wire contract là [API_CONTRACT.md](../architecture/API_CONTRACT.md); nguồn lỗi là [ERROR_CODES.md](../architecture/ERROR_CODES.md).

Endpoint REST trong bảng là mapping hiện hữu; nhãn `[CẦN ĐỔI ĐỂ PHỤC VỤ HTML]` nghĩa cần adapter HTML dùng capability đó, không phải sửa response REST. Admin action dùng version/metadata theo contract; proof tải qua binary proxy no-store.
